## 1. The problem, and the constraints

The problem statement asks for an **offline, air-gapped** tool that analyses bulk
Bitcoin transaction traffic. Three constraints follow from that sentence, and
they shaped every decision in this project:

1. **No network, ever.** Not "at runtime" — the target machine has never seen the
   internet. So: no CDN fonts, no map tiles, no GeoIP service, no package index.
   Everything ships in the repository and CI fails the build if a page grows an
   `http://` reference. Measured: **0 external requests** across 6 pages.
2. **It must be honest about what it knows.** An investigative tool that
   overstates its confidence is worse than one that does less. So every lead
   carries the factors behind its score, every fund trail carries an "estimate"
   marker, and the report states what the model was *not* validated on.
3. **It has to survive a room.** Judges, on a projector, for five minutes. That
   is why the interface leads with charts and why the summary sentence is
   generated by the server from the same numbers the charts draw.

**What it is not.** Not a verdict. Every score ranks a group for review; none of
them establishes guilt. That sentence appears in the product, in the reports, and
in the case dossier.

## 2. Bitcoin, and the five concepts you need

You do not need to know how Bitcoin works to use this tool. You do need five
ideas, because the whole analysis rests on them.

| Concept | Plain words | Why NETRA cares |
|---|---|---|
| **UTXO** | Money is not in an account; it is in unspent outputs, like notes in a wallet. Spending means naming the notes you are using up. | Every input an address spends had to be signed by the same owner, which is the basis of our clustering. |
| **Common-input ownership** | If one transaction spends coins from six addresses, one person controls all six. They had to sign for all six at once. | This is how 1,727 addresses become 533 wallet groups — a **3.24× reduction**. It is a mathematical fact, not a guess. |
| **Change** | Paying someone 1 BTC from a 10 BTC note means you get 9 BTC back, to an address you control. | Detecting change is how "money came back" is separated from "money moved on". Our `change_ratio` feature is this, and it is a defining signal of a peel chain. |
| **CoinJoin / mixing** | Several people pool their coins so nobody can tell whose is whose. | 8 transactions in our dataset are detected as coinjoin-like and **excluded from clustering before anything else**, because a mixing round spends unrelated people's coins together and would otherwise fuse them into one fake "owner". |
| **Fungibility** | Once coins are mixed, no method can say *which* coin went where. | Hence every fund trail is a **proportional allocation**, labelled as an estimate wherever an amount appears. |

**What we cannot see, and say so:** off-chain transfers, coins moved to another
cryptocurrency, and anything that never touched the network traffic we were given.

## 3. Data: synthetic traffic with planted truth

You cannot measure a detector without knowing the answer. So the project ships a
generator that produces traffic *and* the hidden ground truth, counting exactly
which wallet groups are illicit and why.

**Measured, on the shipped dataset:**

| Parameter | Measured value |
|---|---|
| Transactions | **27,860** (12 columns) |
| Capture span | **4.94 days** |
| Distinct addresses | 1,727 |
| Wallet groups after clustering | **533** |
| Planted ground-truth entities | **218** (of which 179 illicit at entity level) |
| File size | 8.76 MB → **314 bytes per row** |
| Distinct transactions | 27,860 (no duplicate txids) |

The generator plants **typologies**, not just labels: peel chains, fan-in
collectors, mixing rounds, cross-border operations, and — importantly — **10
lawful high-volume services as decoys**. The decoys are the point: a detector
that flags every busy wallet is useless, so we plant wallets that *look* busy but
are honest, and report how the model handles them.

Random seed 42, so every number in this document is reproducible.

## 4. Ingestion: the quality gate

**Measured:**

| Parameter | Measured value |
|---|---|
| Formats accepted | `.csv` `.txt` `.json` `.xml` `.sqlite` `.sqlite3` `.db` |
| Rows accepted (shipped CSV) | 27,860 of 27,860 |
| Rows rejected | **0** |
| Rejections and blanked placeholders | none on this file — reported when present |
| Throughput | **31,094 rows/s** (0.896 s for 27,860 rows) |

The design decision worth learning: **the gate runs before anything expensive,
and it is on screen.** Every rejected row is reported with a reason ("bad
timestamp", "output amount mismatch") rather than dropped, because in an
investigation a silently missing row is a missing fact. Hostile input is
rejected with a reason too — the test suite feeds it negative amounts, mismatched
list lengths, placeholder strings like `"N/A"`, and duplicate txids, and asserts
each is either rejected or repaired visibly.

Two specific hardening measures, both in the test suite:

- **Placeholder blanking.** `"N/A"`, `"-"`, `"unknown"` in an *optional* field are
  blanked, not kept as a value that would later be parsed as data.
- **Path traversal.** An uploaded file named `../../evil.csv` is stored under its
  own basename. The API also refuses to read any dataset outside `data/` and
  `uploads/`.

## 5. Correlation: fusing two layers

Most tools analyse the chain and bolt a map on the side. This one **joins them**:
a wallet gets a country because an IP address that broadcast its transactions was
observed in that country.

**Measured:**

| Parameter | Measured value |
|---|---|
| Addresses correlated | 1,725 |
| Wallet groups derived | **533** |
| Addresses per group (mean) | **3.24** |
| CoinJoin transactions excluded first | **8** |
| Control edges (IP → wallet) | 27,860 |
| Flow edges (wallet → wallet) | 27,862 |

Two edge kinds, kept distinct because they mean different things:

- **solid = money moved** — value transferred between two groups. Change
  returning to the sender is excluded: a payment that comes straight back is not
  a payment.
- **dashed = controlled from** — an IP address broadcast transactions for that
  wallet.

The join is what lets the interface say *"this group of six wallets was
controlled from IPs in RU and NL between 02:11 and 02:40"* — a sentence neither
layer could produce alone. When a control edge pointed at a raw IP that was not a
node, the graph drew edges into empty space; the fix was to promote IP endpoints
to first-class nodes (`N-####`), which is why 60 of the 593 payload nodes are
network endpoints rather than wallet groups.

## 6. Features: 28 numbers per wallet group

Every wallet group becomes one row of 28 numbers. These are the model's entire
input — no name, no id, no label. Grouped by what they describe:

| Family | Features | Count |
|---|---|---|
| **Volume and size** | `tx_count`, `tx_sent`, `tx_received`, `log_value_btc`, `value_per_tx`, `mean_payment_btc`, `net_flow_ratio` | 7 |
| **Graph shape** | `fan_in`, `fan_out`, `distinct_counterparties`, `in_out_ratio`, `address_count` | 5 |
| **Network layer** | `ip_count`, `country_count`, `asn_count` | 3 |
| **Time** | `active_days`, `burst_score` | 2 |
| **Typology signatures** | `change_ratio`, `peel_score`, `output_uniformity`, `mixer_score`, `mixer_interaction`, `collector_score`, `exchange_score`, `round_amount_ratio` | 8 |
| **Position in the graph** | `pagerank`, `betweenness`, `community_size` | 3 |

**Measured:** 28 features × 533 groups = **14,924 cells**, built in **5.86 s**.

Two lessons are baked into this table:

- **Log-scale where the range is enormous.** Bitcoin values span nine orders of
  magnitude; an average of an unlogged value describes nobody. `log_value_btc`
  exists for that reason.
- **Robust statistics, not mean and standard deviation.** Attributions are
  computed against a **median/MAD** baseline, and the baseline is **winsorised**
  and shipped inside the model artifact. The reason is in the defect list
  (§16): one enormous transaction was erasing two-thirds of every explanation.

## 7. Machine learning

Four required areas, each with a different job, and each measured against planted
ground truth.

### 7.1 Risk scoring — supervised

`RandomForestClassifier`, class-weighted because illicit is a minority.

| Hyperparameter | Value |
|---|---|
| `n_estimators` | 300 |
| `max_depth` | 12 |
| `min_samples_leaf` | 2 |
| `class_weight` | `balanced` |
| `random_state` | 42 |
| Artifact size | 2,205 KB |

**Measured, and this is the part worth reading.** Two numbers for the same model,
computed two honest ways:

| Evaluation | Precision | Recall | F1 | ROC-AUC |
|---|---|---|---|---|
| **5-fold CV, folds grouped by batch** | **0.931 ± 0.068** | **0.902 ± 0.074** | **0.915 ± 0.063** | **0.991 ± 0.009** |
| Held-out split (1,465 train / 489 test) | 0.907 | 0.867 | 0.886 | 0.981 |

Confusion matrix on the held-out split: **39 TP, 4 FP, 6 FN, 440 TN**.

Why both: the cross-validated figure is the one to quote for "how good is it",
and the held-out figure is the one that catches an overfit. They agree to within
about two points, which is the finding — a single split that looked *perfect* in
v1 (AUC 1.000) was measuring a leak.

**The leak, concretely:** v1 split rows at random. Rows from the same batch are
correlated, and the same wallet appears once per batch, so the model could see a
wallet in training and be tested on it. Grouping the folds by batch closed it:
the mean barely moved and the reported uncertainty **doubled**. That doubled
uncertainty is the honest number.

**Is it just rules?** Three experiments answer this, because "our model is 99%
accurate" is not an answer:

| Experiment | Result | What it means |
|---|---|---|
| Rules alone (the typology detectors) | precision 0.162, recall 0.129, **F1 0.143**, 142 flags | Rules alone are nearly useless as a ranking. |
| Logistic regression on the same folds | AUC **0.762 ± 0.381** | The linear baseline is unstable across batches — near-chance on some. |
| Ablation: the 9 noisiest features removed | AUC **0.993 ± 0.005** | No dependence on a fragile feature set. |

So the signal is in the **feature engineering**, not in the classifier's
cleverness — which is exactly what you want to be able to say.

**Calibration.** Brier **0.020**, expected calibration error **0.015**. A score
of 90 should be right about 90% of the time; this is the measurement that says
whether it is.

**Decoys, measured on held-out predictions only:** 10 lawful high-volume services
planted. In-sample precision@25 1.000; **held-out 0.960**; test 1.000. The
held-out number is the one that counts, because it is the only one the model
could not have memorised.

### 7.2 Anomaly detection — unsupervised

`IsolationForest` (200 trees, contamination 0.06, seed 42) never sees a label. Its
job is to answer "what if criminals do something we never planted?"

**Measured: precision@20 = 0.050 against a base rate of 0.0916** — that is
**worse than chance**, and it is printed in the product rather than dropped. Its
earlier 3.6× lift was an artifact of whole-dataset features and did not survive
window-scale scoring. It is therefore **not used to rank leads**; it is reported
as an honest negative result.

### 7.3 Clustering

Common-input clustering with CoinJoin exclusion. **Measured: adjusted Rand index
0.9988** against planted ownership. Community detection uses greedy modularity
(Clauset–Newman–Moore), measured modularity **0.332** on large transfers only —
small payments are close to random and would drown the pattern.

### 7.4 Evaluation as a discipline

Fold construction, a grouped split, a calibration curve, an ablation, a linear
baseline, a rules-only baseline, and a decoy set. That is the whole reason the
numbers above can be quoted without an asterisk.

## 8. Explanation

A score with no reason is not usable in an investigation, so every lead carries
its own decomposition.

| Parameter | Value |
|---|---|
| Method | **exact decision-path contributions (Saabas)** — *not* Shapley, and named as such |
| Named factors per lead | 8 (plus one combined "smaller factors" term) |
| Reconciliation | `base + Σ listed + other = prediction` |
| **Worst residual across all 77 leads** | **0.0** |
| Leads with an explanation | **77 of 77** |

The design choice that matters: **the printed factors add up to the score above
them.** The payload carries the dropped contributions as one stated remainder, so
the arithmetic is exact rather than "approximately". If the bars did not sum to
the number on screen, the explanation would be decoration — and for most leads it
was, until we fixed it (§16).

The second choice: **exculpatory factors are shown too.** A group whose
`country_count` is 1 and whose `change_ratio` is low gets those recorded as
reasons *against* suspicion. A tool that only ever shows incriminating factors is
not trustworthy.

## 9. Monitoring: the half that is easy to skip

A ranked list is a report. Monitoring is what makes it a tool: the same wallet,
watched over time.

| Parameter | Value |
|---|---|
| Event types | **8** — NEW_ENTITY, ESCALATION, DE_ESCALATION, DORMANT, RESURGENT, CLUSTER_GROWTH, BEHAVIOUR_SHIFT, CLUSTER_MERGE |
| Events recorded on the shipped run | **270** |
| Alert lifecycle | new → acknowledged → investigating → closed_false_positive / closed_escalated / closed_merged |
| Merges detected and recorded | **14** |
| Time to detection | reported per run, per batch, with the window it was first seen in |
| Drift check | PSI **and** KS, both must agree before a feature counts as drifted |
| Drift reference | 28 features, 168 KB, shipped with the model |

Two things this buys that a static list cannot:

- **"How fast did we notice?"** is a measurable property, not a claim. The
  pipeline replays the batches in order and reports the window in which each
  planted entity was first flagged.
- **Drift is stated, not assumed.** When the batch stops resembling the training
  distribution, the anomalies page says so in words and names the worst features
  — because the scores are still the model's output, but its measured accuracy
  does not transfer to a distribution it has not seen.

## 10. The state store and identity

Everything above is per-batch. The store (`out/monitoring.sqlite`) is what makes
the project a *system*: identity, scores, events, and alert state, surviving
between runs.

**Measured, on the shipped run:** 4 batches · 1,725 addresses · 535 groups · 1,912
score rows · 270 events · 80 alert rows → **77 open leads**.

**The hard problem is identity.** A wallet group must be the same group tomorrow,
or "this group escalated from 40 to 92" is a sentence about two unrelated
wallets. v1 numbered entities by rank (`E-0001`, `E-0002`) — deterministic for one
run and wrong the moment the ranking shifts.

The fix: an entity key is derived from **the wallet's own content** — `E-` plus
nine digits of SHA-256 over the lexicographically smallest address it contains.
Two consequences, both tested:

- **Stable across runs.** Re-running the pipeline does not renumber anything.
- **A merge is a finding, not a bookkeeping problem.** When a transaction
  co-spends addresses from two clusters, they are one entity — recorded as a
  `CLUSTER_MERGE` event, with the absorbed key kept as an alias so old links still
  resolve.

That alias table is also what makes the counts agree: an alert raised for a group
that a later batch absorbed is **closed as `closed_merged`** rather than left
open, because a lead the interface cannot open is a broken promise (§16).

## 11. Backend and the frozen contract

One process serves the API and the pages: no CORS, no reverse proxy, one thing to
start. **19 endpoints** (v1 had 12):

| Group | Endpoints |
|---|---|
| Health and state | `/health`, `/windows`, `/reload` |
| The payload | `/results?window=n\|all`, `/events`, `/alerts`, `/monitoring` |
| Ingestion and analysis | `/upload`, `/ingest-report`, `/analyze`, `/job/{id}`, `/jobs` |
| Explanation and method | `/glossary`, `/metrics` |
| **The reports** | `/print/dataset`, `/print/anomalies`, `/report/{entity}` |
| Analyst action | `POST /alerts/{entity}/status` |
| The site | `/` — the six pages, served from the same process (v1 had 12 endpoints in total) |

**Measured:** the whole-capture payload is **1.08 MB**, 593 entities, 77 leads,
187 links, 77 fund trails, built in **32.9 s cold / ~0.09 s warm** (it is cached
to disk); a single-batch payload takes **10.9 s median**.

The **contract** (`schemas/results.schema.json`) is what keeps six pages, three
reports and the API agreeing: **14 top-level properties, 14 definitions, 37.2 KB**,
validated on every run — the fixture in tests, and the payload *as served* by the
API smoke test. A change that drifts from the contract fails the build.

Two design decisions in the backend that were learned the hard way:

- **A job, not a blocking request.** A replay takes ~35 s; holding the request
  open makes the browser time out and the operator watches a spinner with no
  explanation. So `/analyze` returns a job id and the page polls — which is also
  what makes the four-stage progress display honest.
- **Every payload prints its own generation time.** Serving stale analytics is
  invisible: the numbers are valid, just old. That already cost us once, so the
  age of what is on screen is a fact rather than an assumption.

## 12. The web interface

Six pages, in the order of the argument. Each answers one question, each is its
own URL, and each leans on charts rather than prose.

| Page | The question | What is on it |
|---|---|---|
| **Cover** `/` | What is this, and what does it claim? | PS title, team, live numbers read from the running system |
| **Ingest** `/ingest.html` | What did we make of your file? | Drop zone → **quality gate** → four-stage run with the pipeline's own log |
| **Dataset** `/dataset.html` | What is in this data? | One sentence, four figures, five charts, and the examined-vs-flagged grid |
| **Anomalies** `/anomalies.html` | What looks wrong, and why? | Lead cards, plain-word explainers, the evidence waterfall, the money trail |
| **Dashboard** `/dashboard.html` | Where is it, one batch at a time? | Day transport, ranked rail, link graph, evidence panel |
| **Documents** `/documents.html` | How was it built? | These documents, rendered offline |

**Measured:**

| Parameter | Measured value |
|---|---|
| Pages | **6** (v1: 1) |
| Page HTML | 33.4 KB total (largest 8.2 KB) |
| Own JavaScript + CSS | 156.2 KB |
| Vendored libraries | 876.2 KB (`vis-network`, `Chart.js`, 42 font files) |
| Shipped page weight | **189.6 KB** (no fonts) |
| External requests | **0** |
| Build step | **none** — no Node, no bundler, no framework |

Design decisions, each with a reason:

- **Charts before prose.** A judge has five minutes; a chart is read in two
  seconds and a paragraph is not.
- **The one sentence a presenter reads aloud is generated by the server** from the
  same numbers the charts draw, so it cannot contradict them. The qualifications
  that stop it being misread are rendered under it at body size, never folded into
  it — a headline that must be read in full before it is true will be quoted
  without its second half.
- **The examined-vs-flagged grid.** 533 squares, 85 of them coloured. It makes the
  project's central argument — *we examined everything, and this small part is
  what matters* — without a word being read.
- **Explain mode.** Every technical term either has a plain-language replacement
  or carries a dot that opens a two-line explanation. The wording lives in the
  backend (`/glossary`) so the page, the report and the dossier cannot drift
  apart.
- **Dark and light.** One token set, `data-theme` on `<html>`, and charts that
  re-read their colours on toggle. Print is always light: a dark theme burns toner
  and photocopies to mud.

## 15. Tests and CI

**Measured:**

| Suite | Count | Runtime | What it defends |
|---|---|---|---|
| pytest (`tests/test_smoke.py`) | **26 functions** | 16.4 s | contract, ingestion hostile-input handling, identity stability across batches, correlation invariants, attribution reconciliation, drift, outlier robustness, offline assets |

| CI | **17 named steps** | — | the above, plus the offline checks, on every push |

Three testing lessons that are worth more than the counts:

- **A syntax error blanks a page while the server still returns 200.** Route-level
  tests cannot see it, so `node --check` runs over every asset.
- **A clean exit code is not evidence.** The first version of the API smoke test
  passed while testing nothing, because `TestClient(app)` without a `with` block
  never fires the app's startup hooks.
- **A test must not be able to destroy what it tests.** The smoke test posts
  `/analyze`, and a full analysis replaces the stored history — so it now runs
  against a redirected, throwaway directory.

## 16. Every defect we hit, and what it teaches

This is the most useful section in the document. Every entry is a real failure
that reached a running system or nearly did, and the class of mistake it belongs
to.

### 16.1 Silent zeros

| Symptom | Cause | Lesson |
|---|---|---|
| 60 of 85 leads had no explanation | attributions were computed for the top 25 only | A cap that is invisible in the UI reads as a broken feature. Explain everything you claim to explain. |
| The waterfall bars did not add to the score above them | the payload kept the 8 largest contributions and dropped the rest | A truncation without a stated remainder turns a decomposition into decoration. |
| Country bars rendered as 1-pixel slivers | the bar fill was an inline `<i>` with a percentage width — no `display`, so it laid out at zero | Measure the DOM, not the intention. |
| 533 grey squares | the payload said `critical`/`medium`; the stylesheet said `crit`/`med` | A rule that matches nothing does not error. It silently does nothing. |
| An explanation that explained a different score | union mode showed a peak risk but explained the current-batch features | If two numbers are on screen together, prove they came from the same row. |

### 16.2 Numbers that disagree

| Symptom | Cause | Lesson |
|---|---|---|
| "88 open leads" beside "85 flagged groups" | a merge leaves an alert row under a key that no longer names a group | When two counts describe the same thing they must be the same number, or the page must explain the difference. Both were on the cover at once. |
| The cover said 66 leads, the payload said 65 | the merged-away group's alert kept a peak of 53 while the surviving group's own scores never exceeded 10 | An absorbed group's alert is closed as `closed_merged`: the queue must not contain an item no page can open. |
| "27,860 transactions over 5 days" with a fifth bar too small to see | the capture ends mid-day, so a 19-transaction tail became its own "day" | A boundary artefact of our own making is not a finding. A trailing fragment is folded into the day before it — in the splitter *and* in the statistics, by the same rule. |
| "peaking at 22:00" on a flat hourly profile | the busiest of 24 near-equal hours is not a peak | Report the share, and say when the profile is flat. A claim of rhythm needs a slope under it. |

### 16.3 State that goes stale

| Symptom | Cause | Lesson |
|---|---|---|
| A fix on disk that the browser did not apply | heuristic HTTP caching of static assets | Serve `no-cache` (revalidate) when there is no build step. This cost an hour: a correct CSS fix, still-cached, and the page still wrong. |
| A fix on disk that the *server* did not apply | uvicorn is not started with `--reload` | Saving a file does not change a running process. Restart. This caught us twice in one session. |
| A page that rendered empty | it loaded while the store was being rebuilt by a concurrent analyse | A reset-based replay must not run while something is reading — and a test must not trigger one against live state. |
| A fixture that failed a new invariant | `out/smoke.sqlite` was built by the pre-fix code and frozen | Generated artifacts must be regenerated after the producer changes. |

### 16.4 The environment

| Symptom | Cause | Lesson |
|---|---|---|
| `ModuleNotFoundError: numpy._core` | artifacts pickled under numpy 2.x, loaded by 1.x | Pin the interpreter, not just the libraries. |
| Country flags rendered as duplicated letters | Windows has no glyphs for regional-indicator pairs | Test on the machine you will present from. |
| A graph with edges into empty space | control edges referenced raw IPs that were not nodes | A payload is a small graph; a dangling reference is not a smaller truth, it is a wrong one. |

### 16.5 Correctness in the maths

| Symptom | Cause | Lesson |
|---|---|---|
| One huge transaction erased two-thirds of every explanation | mean/std baseline | Median/MAD, winsorised, shipped inside the artifact. |
| `share_of_value` = 1.2 | the denominator counted outputs once while the numerator counted both directions | A share above 1 is not a rounding error, it is a different question being answered. |
| An "87% country mismatch" | our own test joined two unrelated id namespaces | A surprising result is a hypothesis about your code first, and a finding second. We retracted it. |
| AUC 1.000 in v1 | random folds leaked the same wallet into train and test | Be suspicious of a perfect score. Grouping the folds doubled the reported uncertainty — that is the honest number. |

## 18. Glossary

| Term | Plain words |
|---|---|
| **Address** | Where bitcoin sits. |
| **Wallet group / entity** | Addresses proved to belong to one owner, because they were spent together. |
| **UTXO** | An unspent output: a "note" of bitcoin that can be spent. |
| **Peel chain** | Value forwarded through a series of wallets, keeping a little at each step. Layering, in plain sight. |
| **Fan-in collector** | Hundreds of wallets pay one address. The shape of a ransom collection point. |
| **Mixing service** | Coins pooled so nobody can tell whose is whose. Deliberately breaks the trail. |
| **CoinJoin** | A specific mixing technique: many parties contribute equal-value inputs. Detected and excluded from clustering. |
| **Change** | The money returned to the sender when a note is larger than the payment. |
| **Priority / risk score** | 0–100. Ranks groups for review. **Not a verdict.** |
| **Band** | The score grouped: critical ≥ 85, high ≥ 70, medium ≥ 50, low below. |
| **Lead** | A wallet group in a review band. The unit of work. |
| **Alert** | A lead with a lifecycle: new → acknowledged → investigating → closed. |
| **Contribution** | How far one fact pushed a score. These sum exactly to the score. |
| **Residual** | `prediction − (base + contributions)`. Should be 0. Printed so it can be checked. |
| **Drift** | The data stopped resembling what the model was trained on. |
| **PSI / KS** | Two statistical tests for drift. Both must agree here. |
| **Batch / window** | One day of traffic, processed in order. |
| **ARI** | How closely automatic grouping matched known truth, corrected for chance. |
| **AUC** | How reliably the model ranks an illicit group above an innocent one. 0.5 = coin toss. |
| **Brier / ECE** | Whether a score means what it says. Lower is better. |

## 19. Judge Q&A

**"This is synthetic data. Why should we believe any of it?"**
You should not believe it *transfers*. You should believe the **method**: folds
grouped so the same wallet cannot be on both sides, a held-out split, a
calibration curve, an ablation, a linear baseline, and a decoy set of lawful busy
services. Those are the things that would still be right on your data. And the
numbers that came out badly — the unsupervised detector below chance — are in the
product rather than in a drawer.

**"What if criminals do something you never planted?"**
That is what the unsupervised detector is for, and we report honestly that at
batch scale it currently performs **below chance** (precision@20 0.050 against a
0.0916 base rate). It is not used to rank leads. We would rather tell you it does
not work yet than let you rely on it.

**"A perfect score would worry me."**
It worried us. v1 reported AUC 1.000 from a single random split; the leak was the
same wallet appearing in training and test. Fixed, the honest number is
**0.991 ± 0.009** with roughly double the reported uncertainty.

**"Can it be wrong?"**
Every way we know of, and the ways are printed: fund trails are proportional
estimates on a fungible asset; the model is trained on synthetic typologies; a
group of unrelated addresses can be co-spent by an exchange. Hence "lead, not a
verdict" on every page and every report.

**"What stops it from inventing numbers?"**
The contract. 14 properties, 14 definitions, validated on the payload as served by
the API on every run. The one sentence on the dataset page is generated from the
same numbers the charts draw, and the reconciliation line under every waterfall is
arithmetic the payload must satisfy exactly.

**"Why no cloud?"**
Not a preference. The problem statement requires offline operation, so the whole
build is arranged around it: 0 external requests, 42 vendored font files, no
GeoIP service, no package index at install time, and a Docker image that starts
with no setup step.
