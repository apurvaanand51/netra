# Model card

**Team Vortex · SIH 2026 · PS SIH26146** · engine `netra-monitoring-2`

A model card states what a model is for, what it was trained on, how well it does,
and — most importantly — **what it must not be used for**. Written to be read by
someone who has to decide whether to trust the output.

---

## What this system does

Ranks wallet groups by how likely they are to be part of a money-laundering
operation, and attaches the evidence for each rank so an analyst can check it.

## What it is NOT

**A ranked lead, not a verdict.** Every score is a prioritisation for human
review. Nothing here establishes guilt, and no action should be taken on a score
without an analyst examining the evidence beside it.

---

## The models

| | Model | Kind | What it produces |
|---|---|---|---|
| 1 | `IsolationForest` | **unsupervised** — never sees a label | how statistically unusual a wallet group is |
| 2 | `RandomForestClassifier` | **supervised** | the 0–100 priority score |

Plus a **graph algorithm** (common-input ownership → connected components) that
groups addresses into wallet groups, and **rule-based structural detectors**
(peel chain, mixing, collector, exchange) whose outputs become *features* for
model 2 rather than standalone verdicts.

## Training data

- **Synthetic, and deliberately so.** Generated by `generator/generate.py` from a
  fixed seed, schema-identical to fused Bitcoin and network telemetry.
- **27,860 transactions, 532 planted entities, 43 illicit** in the full dataset;
  the monitoring model trains on **1,954 per-batch rows** pooled across five
  batches (179 illicit).
- **Planted typologies:** peel chains, CoinJoin mixing, ransomware fan-in,
  cross-border control — with **hidden labels** the models never see.
- **Decoys included:** 10 lawful high-volume payment processors with regional
  infrastructure, built specifically to look statistically suspicious. Without
  them, "busy" and "criminal" would coincide and precision would be meaningless.

**Why synthetic:** it removes all privacy and legal exposure, and — decisively —
it gives us an **answer key**. Real data has none, which is why most projects can
only claim accuracy rather than measure it.

## Features

**28 features per wallet group**, in four groups:

| Group | Examples | Where it comes from |
|---|---|---|
| Scale | transaction count, total value | the blockchain records |
| Topology | how many wallets paid it, how many it paid | the flow graph |
| **Network layer** | countries of control, distinct IPs, ASNs, timing bursts | **the correlation join** |
| Structural | peel-chain signature, mixer behaviour, collector shape | the domain detectors |
| Graph position | PageRank, betweenness, community size | the graph layer |

The third group is the point of the project: **on-chain data has no geography.**
`country_count` exists only because we joined the IP that broadcast a transaction
to the wallet it moved, and it is a feature the model actually uses.

## Measured performance

Evaluated on held-out planted ground truth. **5-fold cross-validation**, plus a
held-out split as an independent view.

| Metric | Value |
|---|---|
| ROC-AUC (5-fold CV) | 0.993 ± 0.006 |
| Precision (CV) | 0.916 ± 0.043 |
| Recall (CV) | 0.899 ± 0.029 |
| F1 (CV) | 0.907 ± 0.032 |
| Calibration — Brier score | 0.020 |
| Calibration — expected calibration error | 0.015 |
| Wallet-grouping accuracy (ARI) | 0.999 |
| Precision at the top 25 of the rail | 1.000 |

**Monitoring performance** (leave-one-batch-out, the honest figure):
**detection 158/179 = 88.3%, alert precision 91.3%.**

### Why the supervised numbers are high, and why we still print the others

The planted patterns are genuinely learnable from the engineered features, and
these are measured on data the models never saw. The credibility comes from *how*
it is measured, not from the size of the number.

Two results keep the picture honest, and both are reported in the product:

- **A logistic regression reaches AUC 0.995** against the forest's 1.000. The
  margin over a linear model is small: **the feature engineering is doing more
  work than the model choice.**
- **The unsupervised detector now performs worse than chance at batch scale**
  (precision@20 = 0.050 against a 0.092 base rate). Its earlier 3.6× lift was an
  artifact of scoring whole-dataset features. We publish the collapse rather than
  the lift.

There is one more limitation we did not fix: the cross-validation folds are
random and stratified, but rows from the same batch — and the same wallet across
batches — are correlated. Grouped-by-batch CV is the correct method and is
outstanding work. The pooled recall (0.899) is close to the grouped figure
(0.883), so the leak is not inflating the headline, but it is still a leak.

## Intended use

- **Triage.** Deciding which of thousands of wallet groups an analyst opens first.
- **Leads with evidence.** Each rank arrives with the factors that produced it and
  the money trail it follows, so a reviewer can accept or dismiss it quickly.
- **Offline, sovereign deployment.** The whole system runs on a single air-gapped
  machine with no network access, which is what the problem statement requires.

## Out of scope

- **Not evidence of guilt.** A high score means "look here first".
- **Not validated on operational data.** Every number here comes from synthetic
  traffic. Performance on real seized data is **not established** by them.
- **Not for automated action.** No account freezing, no reporting, no enforcement
  decisions without human review.
- **Not multi-chain.** Bitcoin only. Monero and other privacy coins are out of
  scope and are noted as future work.
- **Not a substitute for the underlying records.** Every figure traces to ingested
  traffic; the tool ranks and explains, it does not replace the evidence.

## Explainability, precisely

Each lead carries contributions computed along the entity's decision path through
all trees. They **sum exactly to the score**, and the residual is printed so it can
be checked. The method is named as *exact decision-path contributions, **not**
Shapley*: they are exact along the path but can under-credit feature interactions.
Two different methods are never both called "SHAP".

Where **exact TreeSHAP** is available (when XGBoost is installed — it ships
preinstalled on Colab), the system uses it and reports that instead. Which method
produced a given artifact is recorded in `models/ENVIRONMENT.txt`.

## Fund trails are estimates

Traced fund paths are labelled as estimates everywhere they appear, including in
the case dossier, on the same page as the amounts. Bitcoin is fungible: once coins
are mixed no observer can say which output corresponds to which input, so any
multi-hop trace is an **allocation model**. We allocate proportionally and every
choice is made in the conservative direction — change is excluded so reach is
under-reported rather than overstated. **Do not quote a traced amount without
that statement.**

## Reproducing these numbers

```bash
python tasks.py gen --tx 20000 --clusters 400 --seed 42     # the exact dataset
python -m ml.train --data data --models models               # trains + measures
python -m monitoring.pipeline                                 # windowed replay
```

The dataset is reproducible from a seed, the models are retrained by CI on every
release, and `models/ENVIRONMENT.txt` records the library versions that produced
the shipped artifacts — so the reported numbers cannot drift from the code.
